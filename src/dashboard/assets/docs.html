类人记忆系统

OpenClaw memory-postgres 是一套受人脑启发的长期记忆引擎。它把语义内容和结构化事实分别索引在 Postgres + pgvector 里，用 4 层热度（T0–T3）让常用记忆几乎瞬发，用"新华字典"式多键索引保证从任何角度提问都能命中。

4096qwen3 维度
4 层T0/T1/T2/T3
7 路并行召回
~5%vs 旧 token 成本

① 哲学：为什么要分层

人脑回忆"今天和谁吃了什么"是瞬发的——因为答案早在工作记忆里。OpenClaw memory-postgres 完全照搬这个原理：

  • T0 工作记忆（in-memory，<0.1ms）—— 当前会话最热的 ~50 条 chunks，零成本命中
  • T1 热缓存（PG UNLOGGED 表，~1ms）—— 用户级最近活跃集，跨会话复用
  • T2 主存储（PG + HNSW + GIN + trgm，5–50ms）—— 全量长期记忆
  • T3 冷归档（cold.gists，压缩摘要 + 可下钻原文）—— 历史档案

召回先撞 T0，命中即返；不行才往 T1/T2/T3 兜，并把命中物 promote 回上层热缓存。大多数提问根本不"查"—— 答案已经在最热的层里。

② 写入：6 阶段 Ingest 管道

每条进入系统的内容（用户消息、agent turn、git commit、手工写入）都走完整管道：

  1. Stage 1 — Trash filter（确定性，0 token）正则 / 长度 / 句尾词去掉 70-80% 的"好的、收到、Sure!"等口水句
  2. Stage 0 — Source 信号派生（确定性，0 token）从工具调用、anchors（cwd/branch/PR/file）、time bucket 直接产生索引信号
  3. Stage 2 — Sidecar JSON 解析（0 token）解析 agent turn 末尾的 <mem>{entities,events,prefs,metrics}</mem>
  4. Stage 3 — Cache 查找（0 token）同 hash embedding / entity alias 都从 cache.* 取
  5. Stage 4 — LLM 残差（仅极少 ~5%）前 4 阶段未覆盖的复杂语义内容才请 LLM
  6. Stage 5 — 多键索引（确定性）建立 concept_tag / entity_ref / time_bucket / metric_name / preference_key / event_type / anchor_*
  7. Stage 6 — Reconcile + 写入（事务）实体 dedup、preference supersede 链、event 时间桶去重，全部带 provenance 链回原 chunk
典型一句话"今天和 @shadow 在 openclaw/openclaw 改了 PR #1234，午饭吃了 1800 卡"会一次性产生：1 个 chunk + ~12 条多键索引 + 4 条结构化行（事件/指标/关系），几乎无 LLM 成本。

③ 索引：新华字典式多键

新华字典里一个字可以按拼音、部首、笔画、四角号码查到，不论你怎么入手都能找到。我们对应：

字典查法memory 索引实现
拼音语义向量HNSW + qwen3-4096
笔画关键词全文tsvector + GIN
同音字模糊拼写pg_trgm + GIST
部首概念 tagchunk_indexes(kind=concept_tag)
偏旁实体引用chunk_indexes(kind=entity_ref)
四角号码时间桶chunk_indexes(kind=time_bucket)
—（人脑特有）环境锚点kind=anchor_cwd|branch|pr|file|session

每条 chunk 在 ingest 时强制建立全部相关索引。无论你问"昨天的 PR"、"和 Shadow 干的活"、"calorie 摄入"还是"那个文件改了啥"，都能命中。

④ 召回：并行 7 路 + MMR 重排

每次 query 不让 classifier 提前砍 route——所有索引并行查，让结果质量自己说话：

semanticHNSW cosine on qwen3 4096-d 向量
fulltexttsvector @@ tsquery，bm25 排序
trgmpg_trgm 模糊匹配（错别字、缩写）
concept_tag主题标签精确 / ANY 匹配
entity_ref实体 id 精确匹配
time_bucket时间窗口 ISO 日期
anchorcwd/branch/pr/file/session 强签

合并阶段按归一化分数 + 路由权重融合，MMR 重排去冗余。锚点命中通常 ~10ms 0 token；纯语义召回 ~250ms + 1 次 qwen3 RTT；缓存命中 ~2ms。

⑤ 评分：每次操作 0–100 分

每条 ingest / recall 都计算复合分写入 audit 表，dashboard 上能看趋势：

ingest_score = 100 × (
    0.30 × token_efficiency      // LLM 用量越少越好
  + 0.20 × latency_efficiency    // 越快越好
  + 0.30 × quality_signal        // accept/extractor confidence
  + 0.20 × path_efficiency       // deterministic > cache > sidecar > llm
)

recall_score = 100 × (
    0.25 × token_efficiency
  + 0.25 × latency_efficiency
  + 0.25 × tier_efficiency       // T0=1.0 > T1=0.9 > T2_anchor=0.75 > T2=0.55 > T3=0.2
  + 0.25 × relevance             // 命中是否被 agent 真用，1h 内异步回填
)

权重可在 scoring 配置里调整。Self-tuning（见⑦）会基于这些分趋势自动提建议。

⑥ 后台 Workers

  • Context Primer—— 会话开启时按 cwd / branch 预热 T0/T1
  • Spreading Activator—— 召回命中后异步 promote 邻居（共享 entity / concept_tag 的 chunks）
  • Compactor—— dream phase 把 90 天未召回的 chunks 按 concept_tag 聚类、生成 cold.gists 压缩摘要、原文转 ephemeral 但保留 source_chunk_ids 供下钻
  • Recall Feedback—— recall_count++、warmth_score++、命中的 chunk_indexes.weight 微调（Hebbian-style）
  • Tuning Analyzer—— 见⑦

⑧ 数据库结构

单实例 Postgres 16 + pgvector + pg_trgm + btree_gin，五个 schema：

  • semantic.* — chunks（embedding + 全文 + 多键索引）
  • structured.* — entities / relations / events / preferences / metrics + provenance
  • cache.* — UNLOGGED 表：hot_chunks / embeddings / intent / recall / entity_alias
  • cold.* — gists（压缩归档）
  • audit.* — dream_runs / ingest_decisions / recall_decisions / tuning_proposals

所有结构化行都有 structured.provenance 链回 source chunk。问"你为什么觉得我喜欢 X" 时可以直接 SQL JOIN 出原话。

⑨ Embedding endpoint

所有 embedding 通过你配置的 embedding endpoint（默认通过本地 Tailscale 网络的 OpenAI-compat proxy，地址通过 config.embedding.baseUrl 设置） 调 qwen3-embedding 4096-d。 OpenAI 兼容 /v1/embeddings 协议，按 endpoint 配置可选 Bearer token。 典型一次 embed RTT ~250ms；缓存命中 0 调用。

⑩ 暴露的 Agent 工具

  • memory_search(query, cwd?, branch?, pr?, timeBucket?, limit?) —— 长期记忆查询。带 anchor 走 0 成本路径
  • memory_store(text, importance?, pinned?, cwd?, branch?, pr?, file?) —— 写入事实 / 偏好 / 决定。Discord bot 上可以让用户直接说"记住 X"

Human-Inspired Memory

OpenClaw memory-postgres is a long-term memory engine modeled on how human recall works. It splits semantic content and structured facts into Postgres + pgvector, uses 4 heat tiers (T0–T3) so frequent memories feel instant, and exposes a "Xinhua-dictionary" multi-key index so any angle of asking finds the answer.

4096qwen3 dim
4 tiersT0–T3
7 routesparallel recall
~5%vs old token cost

① Why tiers

Human recall of "what did I eat today and with whom" is instant — because the answer is already in working memory. memory-postgres copies that idea:

  • T0 working set (in-process, <0.1ms) — ~50 hottest chunks per session, zero-cost hit
  • T1 hot cache (PG UNLOGGED, ~1ms) — user-scoped recent set, shared across sessions
  • T2 main (PG + HNSW + GIN + trgm, 5–50ms) — full long-term memory
  • T3 cold archive (cold.gists, compressed summaries + drill-down) — historical archive

Recall walks T0 first; on miss, falls through T1 / T2 / T3 and promotes hits back upward. Most queries don't actually search — the answer is already in the hottest tier.

② Ingest: 6-stage pipeline

Every piece of content entering the system runs the full pipeline:

  1. Stage 1 — Trash filter (deterministic, 0 token)regex / length / closing-word filters reject ~70-80% of "ok thanks"-style filler
  2. Stage 0 — Source-derived signals (deterministic, 0 token)tool calls, anchors (cwd/branch/PR/file), time buckets → direct index signals
  3. Stage 2 — Sidecar JSON (0 token)parse agent's <mem>{entities,events,prefs,metrics}</mem> emitted at turn end
  4. Stage 3 — Cache lookup (0 token)same-hash embeddings, entity aliases pulled from cache.*
  5. Stage 4 — LLM residual (rarely, ~5%)only for content the prior 4 stages couldn't cover
  6. Stage 5 — Multi-key indexes (deterministic)concept_tag / entity_ref / time_bucket / metric_name / preference_key / event_type / anchor_*
  7. Stage 6 — Reconcile + write (transactional)entity dedup, preference supersede chain, event minute-bucket dedup, all linked via structured.provenance
A typical sentence — "today with @shadow on openclaw/openclaw I shipped PR #1234 and ate 1800 cal at lunch" — produces 1 chunk + ~12 multi-key index rows + 4 structured rows (events / metrics / relations) with near-zero LLM cost.

③ Indexes: Xinhua-dictionary style

A Chinese dictionary lets you find a character by pinyin (sound), radical (form), stroke count, or four-corner code — any angle works. We mirror this:

Strokesfull-text keywordtsvector + GIN
Homophonefuzzy spellingpg_trgm + GIST

Every chunk always writes all relevant index rows at ingest. Whatever angle the question takes — "yesterday's PR", "the work with Shadow", "calorie intake", "what changed in that file" — it lands.

④ Recall: 7 parallel routes + MMR rerank

Each query never lets a classifier prune routes — all indexes run in parallel, results speak for themselves:

semanticHNSW cosine on qwen3 4096-d vectors
fulltexttsvector @@ tsquery, bm25 ranking
trgmpg_trgm fuzzy match (typos, abbrev)
concept_tagtopic-tag exact / ANY match
entity_refentity-id exact match
time_bucketISO date window
anchorcwd/branch/pr/file/session strong signal

The merge step normalises scores and applies MMR rerank to reduce redundancy. Anchor hits typically ~10ms 0 token; pure semantic ~250ms + 1 qwen3 RTT; cache hits ~2ms.

⑤ Scoring: every event 0–100

Each ingest / recall computes a composite score persisted to audit; the dashboard charts trends:

ingest_score = 100 × (
    0.30 × token_efficiency      // less LLM = better
  + 0.20 × latency_efficiency    // faster = better
  + 0.30 × quality_signal        // accept rate × extractor confidence
  + 0.20 × path_efficiency       // deterministic > cache > sidecar > llm
)

recall_score = 100 × (
    0.25 × token_efficiency
  + 0.25 × latency_efficiency
  + 0.25 × tier_efficiency       // T0=1.0 > T1=0.9 > T2_anchor=0.75 > T2=0.55 > T3=0.2
  + 0.25 × relevance             // was the hit actually used by the agent within 1h
)

Weights are configurable in scoring. Self-tuning (§⑦) drives proposals from these score trends.

⑥ Background workers

  • Context Primer — pre-warms T0/T1 from cwd / branch on session start
  • Spreading Activator — async promotion of neighbours (chunks sharing entity / concept_tag) after a hit
  • Compactor — during dream phase clusters chunks unread for 90 days by concept_tag, emits cold.gists summaries, demotes originals to ephemeral while keeping source_chunk_ids for drill-down
  • Recall Feedback — recall_count++, warmth_score++, hit chunk_indexes.weight nudged (Hebbian-style)
  • Tuning Analyzer — see §⑦

⑦ Self-tuning loop

The system inspects audit data on cadences and proposes improvements:

⑧ Database layout

Single Postgres 16 + pgvector + pg_trgm + btree_gin, five schemas:

  • semantic.* — chunks (embedding + full-text + multi-key indexes)
  • structured.* — entities / relations / events / preferences / metrics + provenance
  • cache.* — UNLOGGED tables: hot_chunks / embeddings / intent / recall / entity_alias
  • cold.* — gists (compressed archive)
  • audit.* — dream_runs / ingest_decisions / recall_decisions / tuning_proposals

All structured rows carry a structured.provenance link back to the source chunk — "why do you think I prefer X?" becomes a SQL JOIN.

⑨ Embedding endpoint

All embeddings flow through your configured embedding endpoint (set via config.embedding.baseUrl) to a self-hosted qwen3-embedding 4096-d model. OpenAI-compatible /v1/embeddings protocol, no token (broker authenticates by tailnet node identity). Typical RTT ~250ms; cache hits cost zero.

⑩ Exposed agent tools

  • memory_search(query, cwd?, branch?, pr?, timeBucket?, limit?) — long-term memory lookup. With anchors it stays on the 0-cost path
  • memory_store(text, importance?, pinned?, cwd?, branch?, pr?, file?) — write a fact / preference / decision. Lets a Discord user say "remember X" directly
